# TabPals — Approved Plan

1. People & events: global people directory; each event selects members from it. Import members from a previous event via a checklist with select all / select none (covers all, all-except, multi-select). Saved groups (e.g. a family) can be added in one tap. Duplicate person/group names are blocked using Persian normalization.
2. Vouchers: each expense is an accounting voucher with a sequential number per event. Record time (Jalali date, weekday, time) is automatic and immutable; expense date is a separate editable field. Voucher types: expense, contribution to treasurer, settlement payment. An expense may have multiple payers with amounts. Events are open or closed. Closed by end date or manually; closed events block new vouchers; reopening requires a reason and is logged.
3. Audit trail: no voucher is ever deleted. Every edit creates a new revision storing field-level before/after, time and device. Deletion = void with reason.
4. Expense entry flow: big + button. Amount → payer (default = last payer) → description (typed or voice) → "Is everyone's share equal?" Yes = save. No = untick non-participants → "Equal among the rest?" No = set shares per person by weight, percent, or exact amount → show summary and confirm before save. Share_i = amount × w_i / Σw; distribute rounding remainder deterministically so shares always sum exactly to the amount. Calculation engine fully unit-tested.
5. Attachments: photo/video from camera or gallery (images compressed client-side, video capped ~30s), in-app audio recording and audio file upload. Speech-to-text: web = Web Speech API (fa-IR) when online; offline = audio saved and flagged "pending transcription", convertible later with one tap; native Android = system speech recognizer. Keyboard dictation also works in text fields.
6. Multi-user aggregation: all records have global ULIDs; every change is stored as an operation (who, when, device, what). Event creator shares an "invite package" (.tabpal file) so everyone has the same event and member IDs. Users exchange "sync packages" (.tabpal files via WhatsApp/Telegram/share sheet); import merges by ID, deduplicates, and flags conflicting concurrent edits for manual choice, never silently losing data. Optional "ledger keeper" mode. Same operation log will later power online sync.
7. Dashboard: updates instantly after each voucher. Per member: paid, share, balance (debtor/creditor). Event totals. Suggested settlement with minimum number of transfers. One-tap export of the summary as an image ready for WhatsApp. Per-member account statements: available ONLY for closed events (closed manually or by end date). Generated per member, stored inside the event with number, issue date and version history; marked outdated if the event is reopened after issue. Output as image (WhatsApp-friendly) and PDF. Send menu: (1) image/PDF via the system share sheet (WhatsApp, Telegram, Rubika, Bale or any installed app); (2) text summary directly to WhatsApp (to the member's phone if set) or Telegram; (3) SMS with a short summary and a link opening the full statement on the app site, statement data encoded in the URL fragment (no server). Bulk: select several or all members; to one chat = all images shared at once; to each member individually = a send queue with per-member send buttons and sent markers.
8. Backup: zip with selectable components (data only / + images / + audio / + video; all or selected events). Last 5 backups kept in rotation (oldest replaced). Web: stored inside the app, shareable via share sheet; desktop Chromium may also write to a user-chosen folder. Native Android: written to a user-visible device folder with the same 5-file rotation. Restore: replace or merge. Optional password encryption (AES-GCM).
9. Online readiness: layered architecture, repository interfaces with a local Dexie adapter only; sync-ready fields on all records; ONLINE_ENABLED=false. Server choice deferred (must be reachable from Iran).
10. App name defined in one config constant.
11. Native packaging & updates: Capacitor wraps the same web build. Android: GitHub Actions builds a signed release APK (keystore in GitHub Secrets, same key forever), publishes it to GitHub Releases; versionCode derived from package.json version so each APK installs over the previous one keeping data. In-app update check (when online) reads version.json and shows a download link. iOS: Capacitor iOS project generated and kept ready; distribution deferred (requires an Apple Developer account); PWA remains the iPhone install path. PWA and HTML deployment remain unchanged. Native Android: direct send buttons with file attachment for WhatsApp, Telegram, Rubika and Bale.

Theme: system / light / dark, user-selectable. A dedicated visual design stage (2.5) follows Stage 2: cream/olive/gold palette, reversible via a git tag and isolated PR.

Stages: 0 foundation, 1 people & events, 2 vouchers & calculation engine, 3 dashboard & settlement, 4 audit trail, 5 attachments & voice, 6 backup, 7 multi-user sync, 8 dormant online layer, 9 native Android APK & iOS project.

Stage 3 is split into three parts:

- **3A** (done): fixes and foundations needed before the rest of the dashboard can be built — person photos (square, center-cropped, resized/compressed via `src/platform`), drag-and-drop member ordering (`eventMembers.sortOrder`, balances panel follows this order), currency as a تومان/ریال enum (`events.currency`, migrated from the old free-text `currencyLabel`), a custom Jalali date picker and the "weekday + year/month/day, LTR-isolated" date format everywhere a date is shown, per-event treasurer (`treasurerPersonId`, optional card number/IBAN with Luhn/mod-97 validation, changes logged), the balances panel split into a full per-member breakdown (share of expenses, expense payments, fund contributions, treasurer receipts, settlements) instead of mixing fund money into "share", RTL-correct toggle switches, guiding sentences under each wizard step's title, and closed-event read-only rules: the repository layer rejects all member changes (add/import/add group/deactivate/reorder), treasurer changes, and voucher changes on a closed event — only reopening is allowed; vouchers stay fully viewable.
- **3B** (done): per-member statements, the comprehensive event report, treasurer-hub settlement, and a closing-message template bank. Dexie schema v5 adds `vouchers.splitMode` ("equal" | "weight" | "percent" | "exact", migrated from stored participant weights: all-equal → "equal", else → "weight"; percent/exact inputs stay available for display via the existing `participants[].weight`), the `statements` table (`eventId`, `kind`: "member" | "treasurer" | "comprehensive", `personId` — null for the comprehensive report, `number` sequential per event and never reused, `issueVersion` per person+kind, `issuedAt`, a canonical-JSON `snapshot` of everything used to render it so it re-renders identically forever, `templateId`, rendered `closingText`, `verificationCode`, `status`: "current" | "outdated"), and the `messageTemplates` table (`category`: "debtor" | "creditor" | "settled" | "treasurer", `text`, `enabled`, `isDefault`), seeded with the 15 default templates on migration and on first run (Dexie's `populate` hook, since `upgrade()` only runs for pre-existing databases). Reopening an event marks all its "current" statements "outdated"; re-issuing a statement for the same event+kind+person does the same to the one it replaces and bumps `issueVersion`. Setting the event's treasurer for the first time is allowed even while the event is closed (only *changing* an already-set treasurer requires reopening), so a closed event without one can still get a statement issued. Domain additions: `splitExplanation.ts` (the per-row split text shown on member statements), `hubSettlement.ts` (every debtor but the treasurer pays the treasurer; the treasurer pays every creditor; collected − paid-out always equals the treasurer's own balance, since all balances sum to zero), `messageTemplate.ts` (random selection among enabled templates of the right category — chosen once at issue time and stored, never re-rolled on re-render; `{name} {amount} {currency} {treasurer} {event} {balanceText}` placeholder filling; the closing balance line "بدهکار/بستانکار/صاف"), `verificationCode.ts` (canonical JSON + SHA-256, shown as 8 uppercase hex chars "XXXX-XXXX", recomputable in-app from the stored snapshot), and `statementBuilder.ts` (pure member/treasurer/comprehensive data builders, reusing `balanceEngine.ts`'s per-type breakdown for every summary table and `hubSettlement.ts` for the settlement-plan section, with the comprehensive report's control checks — "جمع سهم‌ها = جمع هزینه‌ها", "جمع مانده‌ها = ۰" — computed and checked, not assumed). UI: event screen's "صورت‌حساب‌ها" tab (open-event and closed-without-treasurer prompts, issue-all/per-member/comprehensive actions, the issued-statements list with status chip), a statement view screen with an A4 print stylesheet (repeated table headers, section-aware page breaks — the intended source for Stage 3C's PDF/image export) and a "بررسی اعتبار" recompute-and-compare button, and Settings → "متن‌های صورت‌حساب" (list by category, edit/add/enable-disable, live preview with sample values, "بازگردانی متن‌های پیش‌فرض" which discards edits to default templates and restores the pristine 15 without touching custom ones).
- **3B.1** (done): usability fixes on top of 3B — names, bank details, multi-payer split, wizard navigation, trash & deletion, templates layout. Dexie schema v6 splits `persons.name` into `firstName` (required) and `lastName` (required for new persons; may be empty on a migrated person) — migration splits the existing name on the first space, flags every migrated person `needsNameReview`, and a one-time "بررسی نام‌ها" screen (also reachable later from Settings until all are confirmed) lets each be edited/confirmed. `displayName(person, eventMembers)`: within one event, a member is shown by first name alone, unless another person in the SAME event (active or inactive) shares the same normalized first name, in which case the last name is added in parentheses — used for every "mention" of a member (tables, سهیم‌ها lines, payers, settlement rows, ledger, summaries); the statement header always shows the full name (firstName + lastName); the `{name}` template placeholder is the greeting and uses firstName only; `{treasurer}` uses the treasurer's displayName. Duplicate-person checking now keys on normalized firstName+lastName. Persons gained optional bank details (`cardNumber`, `iban`, `bankName`, `accountHolder`), validated with the existing Luhn/mod-97 validators; `bankName` is auto-suggested from the card's IIN or the IBAN's bank code against a well-known published list of Iranian banks, but a name the user typed is never overwritten. Events gained `treasurerBankName`/`treasurerAccountHolder` alongside the existing card/IBAN; choosing a treasurer prefills all four from that person's saved bank details (still editable per event). A member statement's payment box shows card/IBAN/bank name/account holder, and a treasurer statement's settlement section shows each creditor's saved bank details next to the amount to pay. `vouchers.payerSplitMode` ("exact" | "equal" | "weight" | "percent") records how a multi-payer expense's amounts were derived, reusing the split engine for equal/weight/percent with the same exact-sum rounding guarantee; existing multi-payer vouchers were migrated to "exact". The expense wizard's payer step, when "چند پرداخت‌کننده" is chosen, offers the same mode switch (مساوی/ضریب/درصد/مبلغ) as the share split. Voucher wizards (expense, contribution, settlement) keep all entered data across steps, show a "بازگشت" button on every step after the first, trap the Android/browser back gesture to step back rather than exit, require a confirmation for "انصراف" only when data was entered, and end on a summary step listing every section (amount, پرداخت‌کننده, شرح, تاریخ, تقسیم) with a "ویرایش" link that jumps to that step and returns to the summary — the summary's own confirm button is the only thing that actually saves. Trash: events gained a nullable `deletedAt`; deleting a CLOSED event ("حذف ایونت") sets it (moving it to Settings → "سطل بازیافت", which lists deletion date, "بازگردانی", and a "حذف دائمی" that requires typing the event's title and permanently erases the event plus its members/vouchers/statements in one transaction); restore clears `deletedAt`. An archived person's permanent delete is allowed only when they're referenced by no event anywhere (member or voucher, including events still in trash) — otherwise the sheet shows which events reference them. An archived group's permanent delete has no such restriction. Every permanent delete writes a tombstone operation (`type: "purge"`) for future sync. All of this is enforced in the repository layer, not only the UI. Settings → "متن‌های صورت‌حساب" edits now open a full-screen sheet with an auto-growing textarea and wrapping placeholder chips, and every screen was audited at 360px width to eliminate horizontal overflow (wide statement tables scroll horizontally inside their own container instead of the page).
- **3C**: PDF/image export and all send methods (share sheet, WhatsApp/Telegram text, SMS-with-link).

Stage 6 note: backups must include person photos (Stage 3A added `persons.photo`) alongside the rest of each event's data, and must include trash contents (events with `deletedAt` set, and everything still belonging to them) — an event only leaves a backup once it has been permanently deleted from "سطل بازیافت" (Stage 3B.1).
