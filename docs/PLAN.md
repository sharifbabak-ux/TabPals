# TabPals — Approved Plan

1. People & events: global people directory; each event selects members from it. Import members from a previous event via a checklist with select all / select none (covers all, all-except, multi-select). Saved groups (e.g. a family) can be added in one tap. Duplicate person/group names are blocked using Persian normalization.
2. Vouchers: each expense is an accounting voucher with a sequential number per event. Record time (Jalali date, weekday, time) is automatic and immutable; expense date is a separate editable field. Voucher types: expense, contribution to treasurer, settlement payment. An expense may have multiple payers with amounts. Events are open or closed. Closed by end date or manually; closed events block new vouchers; reopening requires a reason and is logged.
3. Audit trail: no voucher is ever deleted. Every edit creates a new revision storing field-level before/after, time and device. Deletion = void with reason.
4. Expense entry flow: big + button. Amount → payer (default = last payer) → description (typed or voice) → "Is everyone's share equal?" Yes = save. No = untick non-participants → "Equal among the rest?" No = set shares per person by weight, percent, or exact amount → show summary and confirm before save. Share_i = amount × w_i / Σw; distribute rounding remainder deterministically so shares always sum exactly to the amount. Calculation engine fully unit-tested.
5. Attachments: photo/video from camera or gallery (images compressed client-side, video capped ~30s), in-app audio recording and audio file upload. Speech-to-text: web = Web Speech API (fa-IR) when online; offline = audio saved and flagged "pending transcription", convertible later with one tap; native Android = system speech recognizer. Keyboard dictation also works in text fields.
6. Multi-user aggregation: all records have global ULIDs; every change is stored as an operation (who, when, device, what). Event creator shares an "invite package" (.tabpal file) so everyone has the same event and member IDs. Users exchange "sync packages" (.tabpal files via WhatsApp/Telegram/share sheet); import merges by ID, deduplicates, and flags conflicting concurrent edits for manual choice, never silently losing data. Optional "ledger keeper" mode. Same operation log will later power online sync.
7. Dashboard: updates instantly after each voucher. Per member: paid, share, balance (debtor/creditor). Event totals. Suggested settlement with minimum number of transfers. One-tap export of the summary as an image ready for WhatsApp. Per-member account statements: available ONLY for closed events (closed manually or by end date). Generated per member, stored inside the event with number, issue date and version history; marked outdated if the event is reopened after issue. Output as image (WhatsApp-friendly) and PDF. Send menu: (1) image/PDF via the system share sheet (WhatsApp, Telegram, Rubika, Bale or any installed app); (2) text summary directly to WhatsApp (to the member's phone if set) or Telegram; (3) SMS with a short summary and a link opening the full statement on the app site, statement data encoded in the URL fragment (no server). Bulk: select several or all members; to one chat = all images shared at once; to each member individually = a send queue with per-member send buttons and sent markers.
8. Backup: zip with selectable components (data only / + images / + audio / + video; all or selected events). Last 5 backups kept in rotation (oldest replaced). Web: stored inside the app, shareable via share sheet; desktop Chromium may also write to a user-chosen folder. Native Android: written to a user-visible device folder with the same 5-file rotation. Restore: replace or merge. Optional password encryption (AES-GCM).
9. Online readiness: layered architecture, repository interfaces with a local Dexie adapter only; sync-ready fields on all records. Online events arrived in Stage ONLINE-1B (see "Online architecture" below); the server is the separate repo sharifbabak-ux/Tabpals-Live (production base URL https://api.tabpals.ir, must stay reachable from Iran).
10. App name defined in one config constant.
11. Native packaging & updates: Capacitor wraps the same web build. Android: GitHub Actions builds a signed release APK (keystore in GitHub Secrets, same key forever), publishes it to GitHub Releases; versionCode derived from package.json version so each APK installs over the previous one keeping data. In-app update check (when online) reads version.json and shows a download link. iOS: Capacitor iOS project generated and kept ready; distribution deferred (requires an Apple Developer account); PWA remains the iPhone install path. PWA and HTML deployment remain unchanged. Native Android: direct send buttons with file attachment for WhatsApp, Telegram, Rubika and Bale.

Theme: system / light / dark, user-selectable. A dedicated visual design stage (2.5) follows Stage 2: cream/olive/gold palette, reversible via a git tag and isolated PR.

Stages: 0 foundation, 1 people & events, 2 vouchers & calculation engine, 3 dashboard & settlement, 4 audit trail, 5 attachments & voice, 6 backup, 7 multi-user sync, 8 dormant online layer, 9 native Android APK & iOS project.

## Group Order (سفارش گروهی)

Friends at a restaurant each record their own order; the bill is split exactly by what each person ordered, while shared costs (VAT, service, tip, discount) are allocated by a rule the treasurer chooses.

- **Sessions.** One session per meal inside an event (event tab «سفارش‌ها»). Statuses: `draft → open → locked → pricing → finalized`; `open ↔ locked` (admin can reopen); any non-finalized session → `cancelled` (reason required); finalized/cancelled are terminal. Closed events make all sessions read-only (enforced in the repository layer). Finalizing creates ONE expense voucher (`splitMode: "itemized"`, shares = each person's final total, `itemizedSnapshot` with items, shared-item shares and each extra's share) and links it to the session.
- **Admin.** The admin is the event treasurer at session creation. A deputy admin (GO-3) can manage a session in the treasurer's absence, but finalizing always happens on the treasurer's device.
- **Calculation (pure, `src/domain/groupOrder.ts`).** Person subtotal = own lines (qty × unit price) or the optional per-person total when no priced lines, plus weighted share of shared lines. Percent extras apply to the sum of subtotals; each extra is allocated proportional / equal / by weights (discounts negative) with the split engine's exact-sum guarantee. Reconciliation: computed total vs bill total; either block finalize until fixed, or allocate the difference as an extra «اختلاف فاکتور». Waiter list and bulk pricing use Persian name normalization.

| Role | Can do |
|---|---|
| Admin (treasurer) | creates/cancels/locks/reopens sessions, edits anyone's lines, enters orders for people without phones, prices and finalizes |
| Member | edits only their own lines, until the admin locks the session |

Order lines already carry `source` ("admin-device" | "package" | "online") and `sourceVersion` for GO-2/GO-3.

## Online architecture (Stage ONLINE-1B, v0.8.0)

The client talks to the TabPals API (repo `sharifbabak-ux/Tabpals-Live`, `docs/API.md` + `src/permissions.js` are the contract). Base URL: `VITE_API_BASE` (default `https://api.tabpals.ir`), overridable at runtime from Settings («سرور (تنظیم توسعه‌دهنده)»); invite links use `VITE_APP_BASE_URL` (default `https://sharifbabak-ux.github.io/TabPals/`). `ONLINE_ENABLED` (`src/config/app.ts`) is on unless built with `VITE_ONLINE_ENABLED=false`. Offline events are completely unchanged; nothing is ever sent for them.

**Data (Dexie schema v10, additive).** `onlineLinks` (one row per online event: `serverEventId` = the local ULID, `memberId` = this user's person id, `roles[]`, `deviceToken`, `lastSeq`, `status` "uploading" | "online" | "revoked"; the token lives only in IndexedDB — never localStorage, never logged), `outbox` (`++order`, unique `[localEventId+opId]`, sanitized `op`, `attempts`, `lastError`, `rejected`), `appliedRemoteOps` (`[localEventId+opId]`, idempotency). Persons created by sync carry `fromSync` so wiping an event also removes them.

**Synced scope.** Only event-scoped entities: the event, its `eventMembers` and their `persons`, `vouchers`, `statements`, `orderSessions`, `sessionMenuItems`, `orderLines`, `orderPersonTotals`, `sessionExtras`. `groups` and `messageTemplates` are device-local and never synced.

**Security rule — the outbound sanitizer (until Stage ONLINE-1C adds end-to-end encryption).** Every op passes through ONE function, `sanitizeOutboundOp` (`src/domain/outboundSanitizer.ts`, unit-tested to prove nothing private leaves) before it is queued: persons and events use an allow-list (persons: first/last name, archived; events: title, dates, description, currency, treasurer person id, archived/closed/reopen/trash state) so `cardNumber`, `iban`, `bankName`, `accountHolder`, `phone`, `photo`, `note` and the event's treasurer card/IBAN/bank/holder never go out; for every other entity Blobs/binary values and any key that looks like bank/phone/photo data are removed recursively, and a statement's `snapshot` JSON is parsed, scrubbed and re-serialised (so a member's copy of a statement shows the treasurer's name but no card details — and its verification code cannot be re-checked there). The same filter is applied to inbound ops. Local op types map to the server's: close/reopen/outdate/trash/cancel/finalize → `update`; a statement whose only change is `sendLog` → `logSend`.

**Outbound.** `logOperation` (the single choke point of the repository layer) calls `afterLogOperation` inside the writing transaction: it routes the op to its online event(s) (a person's ops go to every online event they belong to), enforces the **local permission guard** (`OnlinePermissionError` aborts the whole write; mirrors the server matrix — members are read-only for all ledger entities, only an admin may purge), completes `create` ops from the stored row, sanitizes and appends to the outbox; adding someone to an online event also queues that person's sanitized `create`. Any read-write transaction that includes `operations` is transparently widened with the sync tables (`TabPalDB.transaction`). The engine's worker drains the outbox in batches (≤ 500 ops, ≤ ~4 MB) with exponential backoff (1 s … 60 s); accepted ops are removed, rejected ops stay with the server's reason (listed for the treasurer, «تلاش دوباره» resends). Members are registered on the server (`POST members`) before they can be invited.

**Go online.** «آنلاین کردن ایونت» (needs a treasurer): `POST /v1/events` (creator = the treasurer person, members = current active members) → token stored → one sanitized `create` op per live row (deterministic ids `snap.<entity>.<id>`, dependency order) queued in the outbox in the same transaction as the link (status "uploading") → uploaded in chunks with a progress bar → "online". Interrupted uploads resume from the persistent queue at the next start.

**Inbound.** Socket.IO with the device token; `ops` are applied through `applyRemoteOperation` (create/update/delete/archive/restore/purge/logSend using the `after` values). It is idempotent (`appliedRemoteOps`, plus ops still pending in our own outbox are skipped), never writes the outbox or the operation log, tolerates unique-index clashes (membership, voucher/statement numbers) and advances `lastSeq`. On connect/reconnect/app start the engine catches up with `GET ops?after=lastSeq` until `hasMore` is false; a gap in a socket batch triggers the same catch-up. `roles-changed` → `GET /v1/me`; `device-revoked`, `event-purged` and any 401 → the event's local data is removed from the device and a persisted Persian notice is shown. When the admin purges deliberately, the local copy stays as an offline event.

**Roles & UI.** Online events show an «آنلاین» badge, the user's role chip and a sync indicator (آنلاین / آفلاین / در حال همگام‌سازی / «n تغییر در صف»; details sheet with rejected ops). A member's device shows everything (members, vouchers, balances, sessions, issued statements) with all add/edit/close/issue controls hidden, plus «صورت‌حساب من» (a live, unissued preview computed locally). **Join flow.** Admin: «دعوت» next to a member without an active device → `POST invites` → sheet with the link `APP_BASE_URL#/join?t=<token>&c=<shortCode>` (the code rides along so the install page can show it; the server reveals it once), an offline QR (same scannability rules as the statement QR), the 8-character code in large letters, copy / share / WhatsApp / Telegram / SMS and the expiry. `#/join?t=…`: in a browser tab (not standalone) → «ابتدا برنامه را نصب کنید» with Android / iPhone steps, the code with a copy button, «سپس داخل برنامه، «پیوستن با دعوت» را بزنید…» and «ادامه در همین مرورگر»; in the installed app → redeems directly (once). «پیوستن با دعوت» (events screen and settings): scan the QR (`src/platform` `QrScanService`: `BarcodeDetector`, jsQR fallback) or type the short code → `POST invites/redeem` → local event shell + `onlineLink` → full catch-up → the event opens.
